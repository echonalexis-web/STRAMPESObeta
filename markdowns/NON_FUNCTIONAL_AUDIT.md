# STRAM-PESO — Non-Functional Testing Audit

**Scope:** Security, Reliability, Availability, Load Resistance
**Method:** Static code review of `server/` (Express + Mongoose) — route middleware chains, schema definitions, connection/error-handling code. Every finding below cites a real file and line.

## Non-Functional Status Summary

The API layer has real, working security controls — role-based auth middleware, `express-mongo-sanitize`, payload-pattern filtering, and a transaction already in place for job applications — but three gaps undermine them under production conditions: rate limiting silently disables itself unless `NODE_ENV=production` is explicitly set on the host, one static-file route grants access to private documents without verifying the auth token it checks for, and the most heavily-queried collection (`JobApplication`) has no indexes. None of the six areas are unaddressed outright; the risk is inconsistent application of patterns the codebase already uses correctly elsewhere.

## Audit Findings Table

| File / Location | Category | Risk Level | Actionable Fix Snippet |
|---|---|---|---|
| `server/server.js:221-236` | Security | **High** | The `/uploads` guard only checks that an `Authorization` header is *present* — it never calls `jwt.verify`, so a garbage or expired token passes, and no ownership check runs against the requested file. Route it through real auth: `const token = req.headers.authorization?.split(" ")[1]; try { req.user = jwt.verify(token, process.env.JWT_SECRET); next(); } catch { return res.status(403).json({ message: "Access denied" }); }` — then add the same `canAccessRef`-style ownership check already used in `fileController.js:9-41`. |
| `server/server.js:62` | Security / Reliability | **High** | `disableRateLimits = ... \|\| process.env.NODE_ENV !== "production"` means every limiter (global, auth, admin, upload) silently no-ops unless the host explicitly sets `NODE_ENV=production` — nothing in `server/.env.example` or the deploy config enforces this. Decouple from `NODE_ENV`: gate on `DISABLE_RATE_LIMITS === "true"` only, and document `NODE_ENV=production` as a required Render env var. |
| `server/models/JobApplication.js` (whole file) | Reliability / Load | **High** | No `.index()` calls despite being queried by `vacancy`, `applicant`, and `status` on nearly every employer/applicant endpoint (`find`, `countDocuments`, `exists` for duplicate-application checks). Under concurrent load this is a full collection scan per request. Add: `jobApplicationSchema.index({ applicant: 1, vacancy: 1 }, { unique: true }); jobApplicationSchema.index({ vacancy: 1, status: 1 });` |
| `server/server.js` (no `process.on` handlers) | Availability | **High** | No `unhandledRejection` / `uncaughtException` handlers exist anywhere in the server. One unawaited promise rejection outside a try/catch can crash the entire process. Add near the top of `server.js`: `process.on("unhandledRejection", (err) => console.error("Unhandled rejection:", err)); process.on("uncaughtException", (err) => { console.error("Uncaught exception:", err); process.exit(1); });` |
| `server/controllers/superadminController.js:195-198` | Data Consistency | **Medium** | `Promise.all([JobApplication.deleteMany(...), JobVacancy.findByIdAndDelete(...)])` is two independent writes, not atomic — a mid-operation failure leaves orphaned applications or a dangling vacancy. Wrap in a session: `const session = await mongoose.startSession(); await session.withTransaction(async () => { await JobApplication.deleteMany({ vacancy: job._id }, { session }); await JobVacancy.findByIdAndDelete(job._id, { session }); }); session.endSession();` |
| `server/config/db.js` | Reliability | **Medium** | `mongoose.connect(process.env.MONGO_URI)` has no pool-size tuning and no connection-state listeners — a lost connection fails silently with no log signal. Add: `mongoose.connection.on("error", (e) => console.error("Mongo error:", e)); mongoose.connection.on("disconnected", () => console.warn("Mongo disconnected — reconnecting..."));` and pass `{ maxPoolSize: 20 }` to `connect()`. |
| `server/controllers/employerController.js` (`bulkUpdateApplicationStatuses`, `bulkScheduleInterview`) | Data Consistency | **Medium** | Bulk endpoints update N `JobApplication` documents via `Promise.all` with no session — a partial failure mid-batch leaves some applications updated and notified, others not, with no rollback. Same `session.withTransaction(...)` pattern as the superadmin-cascade fix above, wrapping the per-application `.save()` loop. |
| `server/controllers/fileController.js:9-41` (`canAccessRef`) | Security / Availability | **Medium** | Grants access only to the file's owner or an `admin` — it never checks "is this user the employer who owns the vacancy this application belongs to," despite `SecureFileLink` being rendered for exactly that case in `EmployerDashboard.jsx`/`RankedApplicantsTable.jsx`. Employers likely get silent 403s opening applicant résumés. Extend the `$or`: check `JobApplication.exists({ resume: ref, vacancy: { $in: employerVacancyIds } })` where `employerVacancyIds` comes from `JobVacancy.find({ employer: userId }).distinct("_id")`. |
| `server/services/storageService.js` (Cloudinary `upload`), `server/services/mailService.js:110` | Availability | **Low** | Neither the Cloudinary upload call nor `transporter.sendMail()` sets an explicit timeout — a hung third-party connection stalls the awaiting request instead of failing fast. Pass `{ timeout: 15000 }` to `cloudinary.uploader.upload(...)`, and wrap `sendMail` in a `Promise.race([...])` against a 10s timeout (mail already degrades gracefully to a console fallback on error — this closes the "hangs instead of erroring" gap). |

## Recommended Stress/Load Testing Strategy

**1. [k6](https://k6.io/)** (free, open-source, scriptable in JS — easiest fit for a JS-stack capstone) — target the two heaviest read paths: `GET /api/jobs` (public browse, unauthenticated, likely the highest-traffic route) and `GET /api/employer/jobs/:jobId/applicants/ranked` (semantic scoring, the most compute-heavy endpoint in the codebase). Recommended defense metrics: **p95 latency < 500ms** and **error rate < 1%** at 50 concurrent virtual users sustained for 5 minutes; this also directly validates whether the `JobApplication` indexing fix above actually holds under load.

**2. [Artillery](https://www.artillery.io/)** (free, YAML-config, fast to set up for auth-flow testing) — target `POST /api/v1/auth/login` and `POST /api/v1/jobs/:id/apply` (the file-upload + duplicate-check + transaction path). Recommended defense metrics: confirm the `authLimiter` actually returns **HTTP 429 at the 51st request within a 15-minute window per IP** (proves rate limiting works once the `NODE_ENV` gap above is fixed), and confirm the apply endpoint returns **zero duplicate applications** when 20 identical concurrent requests are fired at it (proves the existing `jobController.js` transaction holds under a real race, not just sequential testing).
