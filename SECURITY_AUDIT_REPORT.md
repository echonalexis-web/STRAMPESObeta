# Security Baseline Audit Report

## 1. Executive Summary

- **Audit Date:** 2026-09-23
- **Repository:** STRAMPESO_V1A (STRAM PESO — PESO Marinduque job board / SPES platform)
- **Target Framework:** Node.js / Express 4 / MongoDB (Mongoose 8) / React (Vite) client, Socket.IO real-time layer
- **Overall Rating:** MODERATE

This codebase shows a mature, defense-conscious security posture that goes well beyond a typical student capstone baseline: bcrypt password hashing, `tokenVersion`-based session invalidation, `express-mongo-sanitize` + `hpp` + custom payload-injection detection, magic-byte file validation, a dedicated ownership-checked signed-URL file access layer for Cloudinary, timing-safe login responses (dummy hash comparison), and consistent RBAC middleware chaining. The issues found below are real but mostly **narrow, specific gaps** rather than systemic failures — the biggest of which is that the *default* local file-storage driver does not carry the same per-owner authorization the Cloudinary driver enforces, and that most controllers return raw `error.message` to the client regardless of environment.

## 3. Detailed Technical Breakdown for PARTIAL / FAIL Features

### [PARTIAL] JWT / Session Handling
- **Location:** `client/src/context/AuthContext.jsx:44,89,110-111`; `client/src/services/api.js:58,123,164,198,208,219`
- **Vulnerability Summary:** The 30-day bearer token (and the shorter-lived "appeal" token) is stored in `localStorage`, which is readable by any JavaScript running on the page's origin.
- **Root Cause:** `localStorage.setItem("token", tokenValue)` (`AuthContext.jsx:110`) is the sole persistence mechanism; there is no HttpOnly-cookie alternative in this codebase.
- **Impact:** A successful XSS injection anywhere on the SPA (even a third-party script compromise) can silently exfiltrate the token and impersonate the user for up to 30 days. The app's strong output-sanitization posture (`xss` on all string fields, no `dangerouslySetInnerHTML` usage found in `client/src`) substantially reduces — but does not eliminate — this risk vector (e.g. a vulnerable dependency, a future regression, or a browser extension).
- **Suggested Direction:** Not an immediate fix requirement given the mitigating controls already in place, but worth a design note for a future iteration (HttpOnly refresh-token cookie + short-lived access token in memory).

### [PARTIAL] Data / Record Isolation & [PARTIAL] Upload Access Control
- **Location:** `server.js:232-265`; `services/storageService.js:87-95`; `controllers/fileController.js:11-68`
- **Vulnerability Summary:** Under the default `STORAGE_DRIVER=local` configuration, private documents (resumes, valid IDs, business permits, DTI/SEC registration docs, SPES submissions) are written to disk with `visibility: "public"` and served by the generic authenticated-but-not-authorized `/uploads` static handler.
- **Root Cause:** `storageService.js:94` hardcodes `visibility: "public", driver: "local"` for every category when Cloudinary isn't configured, so the category's declared `visibility: "private"` in `CATEGORY_CONFIG` (lines 51-59) is never consulted for the local driver. The `/uploads` middleware (`server.js:232-255`) only checks "is this a valid JWT for *some* user," not "does this user own this file."
- **Impact:** Any authenticated user — jobseeker, employer, or otherwise — who obtains or guesses a document's UUID-based path (e.g. leaked via a shared link, browser history, referrer header, or brute-force of the 122-bit UUID space) can retrieve another user's private ID, resume, or business permit. Practically mitigated by UUIDv4 filenames being unguessable, but this is authentication, not authorization, and violates the principle of least privilege.
- **Suggested Direction:** Route local-driver private categories through an equivalent of `fileController.canAccessRef` (e.g. a `/api/v1/files/local/:token` endpoint that checks ownership before streaming from disk) rather than relying on `express.static` + bare JWT presence.

### [FAIL] Leak Prevention
- **Location:** 87 occurrences of `res.status(500).json({ message: error.message })` across `controllers/authController.js`, `adminController.js`, `spesController.js`, `verificationController.js`, `superadminController.js`, and 11 other controller files.
- **Vulnerability Summary:** Internal error text (Mongoose validation errors, driver errors, occasionally stack-adjacent detail) reaches the HTTP client in every environment, not just development.
- **Root Cause:** Controllers catch their own errors locally and respond directly, rather than calling `next(error)` to let the environment-aware global handler (`server.js:673-690`) apply its `NODE_ENV === "production"` redaction.
- **Impact:** Information disclosure — error messages can reveal schema field names, internal service names, or occasionally raw database error text, aiding an attacker's reconnaissance. Severity is moderate (not typically full stack traces or secrets) but the volume (87 call sites) makes this a systemic pattern rather than an isolated oversight.
- **Suggested Direction:** Either wrap the generic 500 branch of each catch block with a `NODE_ENV` check (mirroring `server.js:686-688`), or standardize on `next(error)` for unexpected failures so the single global handler is the only place that ever renders `error.message` to a client.

### [FAIL] Crash Protection
- **Location:** `server.js` (no matches for `unhandledRejection`/`uncaughtException` anywhere in `server/`)
- **Vulnerability Summary:** No process-level safety net exists for promise rejections or synchronous exceptions that occur outside the Express request pipeline.
- **Root Cause:** The Socket.IO event handlers (`server.js:575-654`) and the top-level `(async () => { await connectDB(); ... })()` IIFE (`server.js:269-705`) have no `process.on("unhandledRejection")` / `process.on("uncaughtException")` registered anywhere to catch an escaping error.
- **Impact:** A single unexpected rejection (e.g. a transient MongoDB timeout inside a Socket.IO handler, which is not try/catch-wrapped) can crash the entire Node process, terminating every user's session and any in-flight request — a self-inflicted denial of service with no attacker action required.
- **Suggested Direction:** Add both handlers near the top of `server.js`, logging the error and performing a graceful shutdown (or, at minimum, preventing an immediate hard crash) rather than leaving the default Node behavior (process exit).

## 4. Prioritized Remediation Plan

1. **High Priority (Immediate Action Needed):**
   - Add `process.on("unhandledRejection", ...)` and `process.on("uncaughtException", ...)` handlers in `server.js` to prevent a single unexpected error from taking the whole process down.
   - Extend ownership-based authorization to the local storage driver's `/uploads` route (or force `STORAGE_DRIVER=cloudinary` in production) so private documents are not accessible to any authenticated user regardless of role.
   - Standardize the 87 `res.status(500).json({ message: error.message })` call sites on either an environment-aware redaction or `next(error)`, so raw internal error text never reaches a production client.

2. **Medium Priority (Next Sprint):**
   - Consider migrating token storage off `localStorage` toward an HttpOnly cookie (or a short-lived in-memory access token + refresh flow) to reduce blast radius if an XSS vector is ever found.
   - Confirm `NODE_ENV=production` is actually set on the live Render/Vercel deployment, since both the CSP policy (`server.js:51`) and the global error-message redaction (`server.js:686`) are conditioned on it.
   - Remove or wire up the currently dead `csrfProtection`/`generateCsrfToken` middleware in `middleware/security.js` (lines 4-26) — it references `req.session`, but no `express-session` middleware is installed anywhere in the app, so this code path can never actually execute (harmless, but dead/misleading code).
